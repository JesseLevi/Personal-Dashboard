# Atom/Button

- **Code:** `components/atoms/Button.tsx`
- **Node ID:** `3623:4346`

CVA variant=filled|outline|white|transparent|destructive (Figma 'Distructive'); Hover/Selected are CSS states. 'Selected' was renamed from 'Active' in Figma 2026-07-20 (ticket #42, mis-naming corrected upstream) — re-fetched node confirms every style's State enum is now Default/Hover/Selected, same fills/text as before the rename, no pixel change. Modelled via `aria-pressed:` (not `active:` — CSS :active means 'being pressed', a different, non-persistent thing), same idiom as Atom/Button-Toggle; caller sets the standard `aria-pressed` attribute, not a new prop. 'With icon'/'With text' modelled as presence of the `icon`/`children` props; icon-only requires aria-label (type-enforced). Figma's Filled/Selected instance has drifted padding (uniform 8px vs 4px/8px elsewhere) — treated as auto-layout drift, not modelled. Hover fill/stroke use the dedicated surface-hover / border-hover semantic tokens (added 2026-07-20; same stone-300/stone-500 primitives, named for their role). Dark mode (ticket #42): surface-raised/surface-hover/surface/border/border-hover/text/text-muted/priority-urgent-bg now carry a dark override in design/tokens.json → emitted as a `[data-theme="dark"]` block in app/theme.css by `pnpm sync:tokens` (that attribute is what @ladle/react's Light/Dark toggle sets on <html>). No Figma dark-mode frames exist for this node, so the dark shades (stone-700/800/900/400, red-950 — all newly added stock-Tailwind primitives, no one-off hex) are this fix's own pick, not a Figma-sourced value; component classes needed zero changes (no `dark:` utilities) since they were already semantic-token-only — the bug was entirely in the token pipeline, which previously emitted no dark values and no dark selector at all.

Tokens renamed to the role/-hover/-active scale; the *-selected colour tokens #52 added were removed (Selected has no background of its own). ## TICKET #68 (2026-07-20)

re-fetched node 3623:4346 again per the ticket's premise that the user re-authored Outline's borders since #58 — confirmed, not assumed: Outline Hover moved stone-400 -> stone-500 (`border-hover`, now the exact value `Atom/Input-field` already used for its Hover, so the two components' Hover tokens are unified — `border-input-hover` deleted), Outline Active moved stone-700 -> stone-800 (`border-active`, Button-only — Input-field's Active is stone-600, a confirmed real difference, not a stale node, so it keeps its own `border-input-active`), and Outline Selected gained a border for the first time (`border-selected`, new, stone-400 — again the exact value Input-field already used, so `border-input-selected` is deleted too). Net: 3 of 4 states are now shared tokens between Button/Outline and Input-field; Active is the one remaining, deliberately-kept divergence. Filled/White/Transparent/Distructive fills are unchanged — this is an Outline-borders-only re-author. Button.tsx's Outline variant gains `aria-pressed:border-border-selected`, which for the first time puts Selected in competition with Hover/Active on `border-color` (previously Selected touched only `text`, a disjoint property, by construction). Verified against the compiled `pnpm ladle:build` stylesheet rather than assumed: Tailwind emits the plain `aria-pressed:border-border-selected` rule *after* `hover:`/`active:`'s border rules, so at equal specificity it would win and silently kill hover/active feedback on a selected button — the exact failure mode `docs/design-tokens.md`'s existing rule was written to prevent. Fixed with two compound variants, `aria-pressed:hover:border-border-hover` and `aria-pressed:active:border-border-active`, each one pseudo-class/attribute term more specific than the plain rules, so they win by CSS specificity regardless of stylesheet order — grepped compiled selectors recorded in the PR. See docs/design-tokens.md (rewritten open question 1 + a new subsection on Outline's Selected-vs-Hover/Active composition) for the full account.
