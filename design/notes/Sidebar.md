## FLAGGED GAP (revised after review, replacing this file's original mid-hover-artifact theory, not appending to it)

the node's active item (Recepten) resolves to Button's `Style=Filled, State=Hover` component (stone-300/surface-raised-hover) rather than `Style=Filled, State=Default` (stone-200/surface-raised) every sibling's own Default instance uses. The original theory (a stray hover capture, drawing on Checkbox's #45 selection-boundary-stroke precedent) does not survive independent pixel-sampling of the fetched component SET: the toggle button reads stone-200 and the active pill reads stone-300 identically in BOTH the Collapsed=No and Collapsed=Yes variant components — two independently-rendered variants agreeing rules out a stray pointer, unlike Checkbox's genuinely single-instance case. This is real, deliberate design. Sidebar.tsx renders the correct pixels by reusing `surface-raised-hover` for this persistent state (Atom/Button `variant="filled"` plus Tailwind's trailing `!` important modifier, `bg-surface-raised-hover!`, to deterministically win the same-property tie against the variant's own default fill rather than gambling on utility generation order) per CLAUDE.md's explicit rule: reuse the existing token for the correct pixels, record the gap.

## REGRESSION caught in review, fixed same PR

a bare resting-only `bg-surface-raised-hover!` outranks every non-important rule on that property regardless of specificity, including Button's own `active:bg-surface-raised-active`, which silently killed the pressed-state feedback docs/design-tokens.md's convention requires ('a selected button must still react to the pointer') — verified in a real browser (resting/hovered/pressed all read identical stone-300 vs. a plain filled control that did darken on press). Fixed with an equally-important `:active`-scoped companion, `active:bg-surface-raised-active!` (same compound-override shape Button/Outline's Selected already uses against Hover/Active) — pressed feedback restored. Hover remains flat, but that is NOT the same problem: the active item's resting colour already equals Filled's own Hover colour, so there is nothing left for `:hover` to move to even with the fix in place (same missing-hover-affordance family as docs/open-questions.md#no-pointer-affordance). The underlying gap (no dedicated selected-fill token) is docs/open-questions.md#selected-needs-a-fill-token — the `!` overrides are a stopgap, not a permanent answer. Icon `Icon/Astroid` (node 3726:2493, Assistant item) maps directly to lucide's own `Astroid` export — an earlier pass wrongly matched it to `Sparkle` by leading numeric coefficients alone (11.017/2.814/1.966) and, on the mistaken belief lucide had no `Astroid` export (a `/asteroid/i` name search missed it — lucide spells it without the middle "e"), briefly vendored the Figma vector as a custom SVG. Rendering both lucide icons side by side against the Figma vector showed lucide's `Astroid` is the real match (same symmetric four-point diamond); `Sparkle` is a visibly different asymmetric twinkle. Fixed to a direct `Astroid` import in Icon.tsx's IconName union. Accessibility: whole component is one `<nav>` landmark (composer-supplied `navLabel`), active item gets `aria-current="page"` (valid on any element, not link-only — these are Button instances, not links, per the fetched node; real href/Link integration is a future composer-level concern, not invented here); toggle is icon-only so its aria-label is a required composer prop (`toggleLabel`, picked per current state, e.g. "Expand sidebar" while collapsed). i18n: navLabel/toggleLabel/labels are all composer-supplied props (same leaf/composer split as CardContainer's addLabel/editLabel), catalog keys under `components.sidebar.*` in messages/{nl,en}.json. Server Component (no "use client"): `collapsed` stays a plain prop, not internal state, since where a real app persists the collapsed flag (cookie/localStorage/URL) genuinely varies by caller, unlike Dropdown's identical-for-every-caller disclosure state.
