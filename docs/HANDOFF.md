No Docker on this dev machine — nothing here has been exercised against live Supabase or a real device, and #96's acceptance was never run in a browser. Close before trusting the app in production.

**`deploy.yml` now works end-to-end (#165, 2026-08-07)** — first successful run ever, both jobs green. Production (`personal-dashboard-orcin.vercel.app`) is live on `main` via the workflow's own `vercel deploy --prebuilt --prod`, currently at commit `f1784a2` (includes #161/#163's NEVO data — `reference.ingredients` 2328 rows / 53 `per_100ml` / 7 fibre-NULLs; `reference.ingredient_unit_masses` 1175 rows / 1026 ingredients). Getting there took five fix-and-retrigger cycles; worth knowing if this breaks again:
- **The workflow was missing `corepack enable`** — `vercel build` spawn-failed on `pnpm` since Node 24 doesn't shim it by default. Fixed in the workflow itself.
- **A Vercel token scoped to a single project failed** with "Could not retrieve Project Settings" against `vercel pull`/`build`/`deploy` in CI, despite correct `VERCEL_ORG_ID`/`VERCEL_PROJECT_ID`. An account/team-scoped token fixed it — corrected guidance in ADR-0012 §4.
- **A migration applied by hand or via the Supabase MCP server gets that route's own timestamp as its version**, not the repo's filename — `supabase db push` then refuses, seeing a remote version with no matching local file. This bit five migrations (#161/#163's two, plus three from #149/#153/#155 applied 2026-08-02) before `supabase_migrations.schema_migrations.version` was corrected by hand for all of them. Expect the same reconciliation step every time a migration reaches the hosted project outside `deploy.yml`.
- **Never batch a large migration across parallel agents.** Doing so on #161 raced two writers into 250 duplicate `reference.ingredients` rows, cleaned up afterwards with `delete … using … where a.ctid > b.ctid`. Apply migrations in a single call, sequentially.
- **Committing a migration does not apply it.** `deploy.yml` is `workflow_dispatch`-only, so a push to `main` builds and deploys code but migrates nothing. #164's `20260807000001_usda_unit_masses.sql` sat committed-but-unapplied from `effdfc5`, which is why cup↔gram conversion and every cup-based macro read as `?`/ml/ounce in the hosted app while the code was correct. **When a feature depends on new data, check `supabase_migrations.schema_migrations` on the hosted project before debugging the code** — `select count(distinct ingredient_id) from reference.ingredient_unit_masses where unit='cup'` returning 0 found this in one query.
