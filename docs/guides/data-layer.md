# Guide: data, schema & product rules

Read this before touching `supabase/`, server components/actions, or any user-facing string. Referenced from `CLAUDE.md`.

Fundamentals (multi-user + RLS, NL/EN i18n, security-by-design) are decided in `Vision.md` §2 — don't relitigate them. Applied in code:

- **All data access goes through Next.js server code** (server components/actions) — the browser never talks to Supabase directly, and `service_role` never leaves server/worker modules (ADR-0002/0003).
- Every table gets a `user_id` foreign key and a Row Level Security policy, **plus an RLS test in `supabase/tests` in the same PR** (copy `rls-profiles.sql`) — CI fails on untested tables (ADR-0009). Schema changes only via `supabase/migrations`.
- **Schema changes reach production through CI, not by hand** (ADR-0012) — but only when the user runs it. `.github/workflows/deploy.yml`'s `migrate` job runs `supabase db push` against the hosted Supabase project; its `deploy` job builds/ships the app to Vercel production after `migrate` succeeds. Neither job fires on merge — the workflow is `workflow_dispatch`-only (ADR-0012, amended 2026-08-02: the user promotes to production manually, not automatically on every merge), so a migration merged in your PR does **not** reach the hosted database until the user explicitly runs the workflow (or applies it by hand, ADR-0012 §5). Studio/psql edits against the hosted project remain forbidden (ADR-0009); the one-time exception for the two Phase 4 migrations that predate this mechanism is documented in ADR-0012 §5.
- **A new table's migration must also grant table access**: `grant select, insert, update, delete on public.<table> to authenticated;` and `grant select on public.<table> to anon;`. RLS policies are the real boundary, but without the grants every query fails with `42501 permission denied` — this project's Supabase does not auto-expose new tables. Copy the grants block in `20260720000001_profiles.sql`.
- **A non-`public` schema also has to be exposed on the Data API, and that setting is NOT in this repo.** `supabase/config.toml`'s `[api].schemas` configures the **local** stack only. On the hosted project the equivalent is a stored dashboard setting (Settings → Data API → Exposed schemas), so a schema can be fully migrated, granted and RLS'd and still return `PGRST106 Invalid schema` in production. This bit `reference` (added by `20260730000001_ingredient_library.sql`; `lib/recipes/queries.ts` reads it in two places). **Current hosted state: worked around at the role level, not via the dashboard** — `alter role authenticator set pgrst.db_schemas = 'public, graphql_public, reference'` plus `notify pgrst, 'reload schema'`. Verified working (PostgREST returns 200 for `Accept-Profile: reference`), but know the two consequences before touching it: the role-level value **shadows the dashboard toggle**, so changing Exposed schemas in the UI no longer has any effect; and `supabase gen types` still reads the *stored* setting, which is why generated types omit `reference` and drop the `public.ingredients.reference_id` FK. The clean end state is to set Exposed schemas in the dashboard and then drop the role override — until someone does, this override is load-bearing and lives nowhere in version control.
- **CI gate (#190): `lib/database.types.ts` drift is checked in the `db` job, and the file is now fully generated — never hand-edit it.** After `supabase start`, the job runs `pnpm db:types` (`supabase gen types typescript --local --schema public,reference > lib/database.types.ts`), and separately checks `git diff --exit-code lib/database.types.ts`. Run the same two commands locally once Docker/the standalone CLI exist on a machine — not possible on this dev machine, see `CLAUDE.md`.
  - **Why the `reference`-skip above doesn't block this gate**: that problem is specific to generating types against the **hosted/linked** project (`--linked` / `--project-id`) — the Management API endpoint behind those flags reads the *stored, dashboard* Exposed Schemas setting, which this project's role-level override shadows without updating. `--local` generation is a different CLI code path entirely (verified against the CLI's Go source, `apps/cli-go/internal/gen/types/types.go`): passing an explicit `--schema` list (as `db:types` already does) makes the command use exactly that list, skipping the `config.toml`-`[api].schemas` fallback altogether; and `--local` runs a `postgres-meta` Docker container that introspects the local Postgres catalog directly, never through PostgREST's schema-exposure role config. The hosted-only role override is also never applied to the local/CI stack — it lives only on the hosted project. Confirmed by the first real CI run on #190's PR: the `reference` schema, its `ingredients`/`ingredient_unit_masses` tables, and the cross-schema `Database["public"]["Enums"]["recipe_unit"]` reuse all generated correctly.
  - **What the first CI run actually caught instead**: the file had been hand-maintained (no Docker on this dev machine to regenerate it) against a stale output *format*, not just stale content. The real `supabase gen types` now emits `export type Database = {...}` (not `export interface Database`), no trailing semicolons, tables in alphabetical order, and a whole trailing block of helper types (`Tables<>`, `TablesInsert<>`, `TablesUpdate<>`, `Enums<>`, `CompositeTypes<>`, `Constants`) the hand-written file never had.
  - **`public.ingredients.reference_id`'s FK generates with `Relationships: []`**, not a `foreignKeyName` entry, even though `reference` is included and the FK exists in the migration (`20260730000001_ingredient_library.sql`). This is real generator behaviour for this cross-schema FK, not a bug to "fix" by hand-adding the relationship back — `lib/recipes/queries.ts` never relies on it (it resolves the link with two separate queries: select `reference_id` from `public.ingredients`, then a second `.schema("reference")` query keyed on that id — never PostgREST's embedded-join syntax), so the empty array costs nothing at the call sites.
  - **If the `db` job goes red on a future PR**: don't hand-patch the diff shown in the Actions log. The job uploads the freshly regenerated file as the `database-types` artifact on every run (`if: always()`, so it's there even when the diff step fails) — download it (`gh run download <run-id> -n database-types`) and commit those bytes as-is. Any hand adjustment (fixing formatting, restoring a comment, restoring a Relationship) reintroduces drift the next time the gate runs.
  - **Table/type history that used to live in a header comment inside the file** (now gone, since the file must byte-match generator output): `#91` profiles, `#119` recipe schema (`recipe_categories`, `recipes`, `recipe_ingredients`, `recipe_steps`, `tags`, `recipe_tags`), `#130` the `reference` schema + `public.recipe_unit` enum (ADR-0011 §3 — created in `public`, reused cross-schema by both `ingredient_unit_masses` tables), `#149` `recipe_step_ingredients` + `replace_recipe_contents` RPC, `#161` `reference.ingredients` gains `fiber_g_per_100g`/`nutrient_basis`/`category_nl`/`category_en`, loses `category` (ADR-0013) — `nutrient_basis` generates as plain `string`, confirming Postgres `check (nutrient_basis in (...))` constraints don't surface as TypeScript literal unions, `#169` `move_card`/`move_recipe` RPCs, `#175` `shopping_list_items`. Further per-table detail lives in each migration file's own header in `supabase/migrations/`, and full history is `git log -- lib/database.types.ts`.
  - **The CLI is pinned to `version: latest` in `ci.yml`, deliberately, not pinned to a fixed version.** Consequence: the `db` job can go red purely because Supabase shipped a new codegen template (as happened above), with zero schema change on this project's side. Treat that as "adopt the newly generated file" (via the artifact, per above), not as a gate to revert or a schema bug to chase.
- Ownership is user_id-only per ADR-0001 — no household/sharing structures, not even "convenient" ones.
- Per-account secrets (AI keys, calendar credentials) go through the Vault pattern of ADR-0002 — never plaintext, never logged, decrypted only server-side.
- No hardcoded user-facing strings — everything through next-intl catalogs (`messages/nl.json` + `messages/en.json`, both filled in the same PR — ADR-0007).
- Render stored rich text only through TipTap's React renderer (fixed extension whitelist); render AI-agent output as plain text. Never `dangerouslySetInnerHTML` on user or model content.
- `Vision.md` lists explicit "buiten scope" items per module — treat those as real boundaries, not backlog.
