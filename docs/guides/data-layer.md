# Guide: data, schema & product rules

Read this before touching `supabase/`, server components/actions, or any user-facing string. Referenced from `CLAUDE.md`.

Fundamentals (multi-user + RLS, NL/EN i18n, security-by-design) are decided in `Vision.md` §2 — don't relitigate them. Applied in code:

- **All data access goes through Next.js server code** (server components/actions) — the browser never talks to Supabase directly, and `service_role` never leaves server/worker modules (ADR-0002/0003).
- Every table gets a `user_id` foreign key and a Row Level Security policy, **plus an RLS test in `supabase/tests` in the same PR** (copy `rls-profiles.sql`) — CI fails on untested tables (ADR-0009). Schema changes only via `supabase/migrations`.
- **Schema changes reach production through CI, not by hand** (ADR-0012) — but only when the user runs it. `.github/workflows/deploy.yml`'s `migrate` job runs `supabase db push` against the hosted Supabase project; its `deploy` job builds/ships the app to Vercel production after `migrate` succeeds. Neither job fires on merge — the workflow is `workflow_dispatch`-only (ADR-0012, amended 2026-08-02: the user promotes to production manually, not automatically on every merge), so a migration merged in your PR does **not** reach the hosted database until the user explicitly runs the workflow (or applies it by hand, ADR-0012 §5). Studio/psql edits against the hosted project remain forbidden (ADR-0009); the one-time exception for the two Phase 4 migrations that predate this mechanism is documented in ADR-0012 §5.
- **A new table's migration must also grant table access**: `grant select, insert, update, delete on public.<table> to authenticated;` and `grant select on public.<table> to anon;`. RLS policies are the real boundary, but without the grants every query fails with `42501 permission denied` — this project's Supabase does not auto-expose new tables. Copy the grants block in `20260720000001_profiles.sql`.
- **A non-`public` schema also has to be exposed on the Data API, and that setting is NOT in this repo.** `supabase/config.toml`'s `[api].schemas` configures the **local** stack only. On the hosted project the equivalent is a stored dashboard setting (Settings → Data API → Exposed schemas), so a schema can be fully migrated, granted and RLS'd and still return `PGRST106 Invalid schema` in production. This bit `reference` (added by `20260730000001_ingredient_library.sql`; `lib/recipes/queries.ts` reads it in two places). **Current hosted state: worked around at the role level, not via the dashboard** — `alter role authenticator set pgrst.db_schemas = 'public, graphql_public, reference'` plus `notify pgrst, 'reload schema'`. Verified working (PostgREST returns 200 for `Accept-Profile: reference`), but know the two consequences before touching it: the role-level value **shadows the dashboard toggle**, so changing Exposed schemas in the UI no longer has any effect; and `supabase gen types` still reads the *stored* setting, which is why generated types omit `reference` and drop the `public.ingredients.reference_id` FK. The clean end state is to set Exposed schemas in the dashboard and then drop the role override — until someone does, this override is load-bearing and lives nowhere in version control.
- **CI gate (#190): `lib/database.types.ts` drift is checked in the `db` job.** After `supabase start`, the job runs `pnpm db:types` (`supabase gen types typescript --local --schema public,reference > lib/database.types.ts`) and fails on `git diff --exit-code lib/database.types.ts`. Run the same two commands locally once Docker/the standalone CLI exist on a machine — not possible on this dev machine, see `CLAUDE.md`.
  - **Why this isn't blocked by the `reference`-skip above, and needed no code change**: that problem is specific to generating types against the **hosted/linked** project (`--linked` / `--project-id`) — the Management API endpoint behind those flags reads the *stored, dashboard* Exposed Schemas setting, which this project's role-level override shadows without updating. `--local` generation is a different CLI code path entirely (verified against the CLI's Go source, `apps/cli-go/internal/gen/types/types.go`): passing an explicit `--schema` list (as `db:types` already does) makes the command use exactly that list, skipping the `config.toml`-`[api].schemas` fallback altogether; and `--local` runs a `postgres-meta` Docker container that introspects the local Postgres catalog directly, never through PostgREST's schema-exposure role config. The hosted-only role override (`alter role authenticator set pgrst.db_schemas = ...`) is also never applied to the local/CI stack — it lives only on the hosted project, nowhere in version control. So `pnpm db:types`'s existing `--schema public,reference` was already correct for CI's fresh local stack (which also lists `reference` in `config.toml`'s `[api].schemas` regardless); #190 only needed the gate step, not a schema-argument or role-override fix.
  - Not independently verified by this ticket: whether every hand-written field in the committed `reference` block (e.g. `nutrient_basis: string` for a `check (nutrient_basis in (...))` column) matches a real `postgres-meta` run byte-for-byte — that can only be confirmed by the CI run itself, since this dev machine has no Docker.
- Ownership is user_id-only per ADR-0001 — no household/sharing structures, not even "convenient" ones.
- Per-account secrets (AI keys, calendar credentials) go through the Vault pattern of ADR-0002 — never plaintext, never logged, decrypted only server-side.
- No hardcoded user-facing strings — everything through next-intl catalogs (`messages/nl.json` + `messages/en.json`, both filled in the same PR — ADR-0007).
- Render stored rich text only through TipTap's React renderer (fixed extension whitelist); render AI-agent output as plain text. Never `dangerouslySetInnerHTML` on user or model content.
- `Vision.md` lists explicit "buiten scope" items per module — treat those as real boundaries, not backlog.
