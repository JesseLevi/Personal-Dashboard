# Guide: UI components (Figma → code)

Read this before building or changing anything in `components/` or `app/`'s UI. Referenced from `CLAUDE.md`.

## Design system: Figma → code, Atomic Design

The Figma file ("Notion - V2") is the source of truth for UI, mirrored 1:1 into `components/{atoms,molecules,organisms}/` after Figma's Atomic Design sections (folder ↔ section map: `Architecture.md` §2). Rules:

- **Component names match Figma layer names.** `Atom/Button` → `components/atoms/Button.tsx`; `Card-content/Recipi` → `components/molecules/CardContentRecipe.tsx` (translate NL→EN in code, keep the mapping obvious). This is what keeps the Figma↔code link traceable.
- **Before building or changing a UI component, fetch it from Figma via MCP first** (`get_figma_data` with the relevant node-id). Don't guess spacing, colour, or type scale from memory or a screenshot — pull it from the dev-ready node. Note the node-id in the PR/commit description.
  - **`get_figma_data` silently drops Dev Mode annotations.** The MCP (`figma-developer-mcp`) returns layout/fills/components only — there is no `annotations` field in its payload, so a node's interaction notes look like they don't exist. They do: the REST API returns them (`GET https://api.figma.com/v1/files/<fileKey>/nodes?ids=<nodeId>`, header `X-Figma-Token`, key already in `.mcp.json`), on each node as `annotations[].label`. **Check them whenever a ticket touches interaction** (what a click opens, motion direction, drag behaviour, empty/first-load states) — the Te-Doen section alone carries 45 of them, and they answered six questions that the geometry payload left open. Geometry from MCP, behaviour from annotations.
  - **The agent that writes the component does the fetch itself** — first tool call of the build. A second-hand summary pasted into the prompt is not a substitute: it drops fidelity and defeats the point of a live dev-ready pull. When delegating, tell the subagent to call MCP for its node; do not pre-digest the node into the prompt and skip the fetch.
  - **Pixel-parity is verified, not assumed.** Fetch the visual with `download_figma_images`, render the Ladle story, compare, and record the check (and any intentional deviation) in the PR. The ADR-0010 Ladle/Playwright screenshot baseline now enforces this locally — run **`pnpm test:visual`** before opening the PR, and `pnpm test:visual:update` when a change to the design is intended (review the regenerated PNGs like any other diff). In CI the job is still **non-blocking** until Linux baselines exist (#6), so a local run is not optional yet.
  - **Icons: Figma layer names are the exact lucide export names** (`Icon/Ellipsis`, not `Icon/Dots`), so the `Icon` atom's mapping is a direct lookup and the rendered glyph really is the vector Figma shows. **Never trust the name alone** — render the candidate export (`renderToStaticMarkup` or the Ladle story) and compare its paths against the Figma node. Same-named exports can be "false friends" (lucide's `Cross` is a medical/plus glyph, not an X), and shape-verification has already caught three real mismappings. If no lucide export matches, that's an Architecture-level call (custom SVG vs. exporting Figma's vector) — flag it, never hand-draw an approximation.
- **Never build a component that doesn't exist in Figma yet.** If a ticket needs undesigned UI, stop and flag it rather than inventing a layout — send it back through the Fable/Figma loop instead of freelancing.
- **Compose exactly as Figma nests.** If Figma builds `Card-container` out of `Card` instances wrapping `Card-content/*` in a slot, the React tree mirrors that composition — don't flatten it. Dependencies flow one way only: atoms ← molecules ← organisms ← `app/`; an atom never imports a molecule.
- **Variants via CVA**: Figma variant properties (Style, Type) → CVA props; **State (Hover/Active/pressed) → CSS pseudo-classes, never props**; Figma booleans (`With icon`) → optional props; Figma SLOT nodes → `children`/named slots.

The full component update loop (node-id → fetch → update → Ladle screenshot diff → PR) lives in `Architecture.md` §3.3 / ADR-0010.

## Component code conventions (house style — locked in by the Phase 2 atoms)

These exist because the first parallel component work diverged on each of the points below. Follow them so components read as one hand:

- **Server Component by default.** A presentational atom/molecule (no event handlers, no hooks) must NOT carry `"use client"`. Interactivity is wired by the composing molecule/organism, not baked into the leaf atom. Add `"use client"` only when the component itself owns state/handlers.
- **`className` merging is not ad-hoc.** Variant components use `cva()` and pass caller `className` through its `class`/`className` arg. Non-variant components merge with **`clsx`** (already a dependency). Never concatenate class strings by hand, and never drop a caller's `className` on the floor.
- **Icons go through the `Icon` atom only.** `Icon` is the single module that imports `lucide-react`; every other component renders icons as `<Icon name="…" />`. The `IconName` union is the Figma vocabulary (spelling-corrected, e.g. `Calendar` not `Calandar`), kept identical to lucide's export names so each entry is a direct PascalCase lookup to the identically-named export (see `Icon.tsx`'s header and the icon rule above). Because `Icon.tsx` is the only place lucide is imported, a lucide-side rename is absorbed there in one edit rather than rippling through call sites. Decorative icons get `aria-hidden`; an icon that IS the control's label gets its accessible name on the wrapping control.
- **Accessibility is part of the atom.** Form-shaped presentational atoms expose semantics: e.g. `Checkbox` renders `role="checkbox"` + `aria-checked` rather than a bare styled `<div>` or a misleading `readOnly` native input. Decide input-vs-role deliberately and note it in the PR.
- **Ladle stories use Tailwind utility classes, never inline `style={{…}}`** — even though stories are dev-only, they showcase the design system and must model correct usage (token classes, not raw px/hex).
- **Raw hex never appears in `components/`, not even in comments.** `check:server-only` greps the whole file, so documenting a mapping as `bg #E7E5E4` fails the build. Describe colours by their primitive/token name (`stone-200` → `surface-raised`); the exact Figma hex belongs in `design/notes/<Component>.md`, which is the design-source record and is not grepped.
- **A token gap is flagged, never papered over.** If Figma uses a value that has no matching *semantic* token (e.g. a hover fill that happens to equal the `border` token), reuse the existing token for the correct pixels **and** record the gap in `design/notes/<Component>.md`, with a one-line flag in the component pointing at it, so the token sync can add a real token later. One line in code, the full record in the note file — not the same account twice (see "Comments in component source" below). Never hardcode the hex, and never silently normalise the design to a different colour.
- **Comments in component source are a budget, not a diary.** Enforced by `pnpm check:comment-budget` (CI): max **30%** comment lines per file (files under 25 comment lines are exempt — a small, honestly documented component is legitimately 40% comment, and oversized headers are caught by the block rule anyway), max **15 lines** per comment block, and **no ticket narration** — a bare pointer like `(#68)` is fine, retelling what ticket N changed is not.

  What belongs *in the component*: the `// figma: node-id=…` line; a header of at most ~8 lines naming the Figma component and mapping its variant axes onto props/slots/CSS states; a one-or-two-sentence warning wherever the code is non-obvious enough that an editor would break it; active token-gap flags. Cite the source rather than repeating it — `// Selected only sets color, so it composes with hover/active — never add a bare aria-pressed:bg-* here. See design/notes/Button.md.`

  What belongs in **`design/notes/<Component>.md`**: ticket-by-ticket history, measurement write-ups, the state/pixel matrix, alternatives considered and rejected. That file *is* the design record (`design/notes/README.md`); a component that also tells the story creates a second home for the same fact, and the two drift. This rule exists because they did: `Button.tsx` reached 262 comment lines against 72 of code, all of it a lossier copy of `design/notes/Button.md`.

  Never explain in prose what the code plainly states, and never restate a rule that already lives in `CLAUDE.md` or this guide.

- **Don't invent Figma states that aren't in the fetched node.** If `design/notes/<Component>.md` notes a variant/state the dev-ready node doesn't actually contain (e.g. Checkbox's "delete"), build only what Figma exposes and leave the gap flagged in that note for triage — never freelance the missing state (reinforces the "never build what isn't in Figma" rule above).

## Design tokens (ADR-0010)

Pipeline: Figma variables → `design/tokens.json` (`pnpm sync:tokens`) → generated `app/theme.css` (Tailwind v4 `@theme`) → utility classes (full detail in `Architecture.md` §3.2). Never hand-edit generated theme files; never use a raw value where a semantic token exists (enforced by `check:server-only`).

- **Figma text styles are Tailwind-native**: `text-xl/semibold` → `text-xl font-semibold`. Translate a returned `textStyle` directly into that class pair — don't re-derive size/line-height/weight by hand.
- **The token scale is closed.** If a Figma value has no Tailwind-scale/semantic equivalent, check with the user before inventing a one-off — never hardcode the hex.
- **`design/figma-map.json` is the canonical component↔node-id map** and holds *only* name → path → node-id; every component carries `// figma: node-id=...` in its header. The per-component design record (discrepancies, token gaps, ticket history) is `design/notes/<Component>.md` — one file per component, so parallel agents never conflict on it. Adding a component = map entry + note file + header annotation + Ladle story, all in the same PR.

## Design-system state: what is still true

**Colour states live in `docs/design-tokens.md`** — the `role`/`role-hover`/`role-active`/`border-selected` scale, why Selected must keep composing with Hover/Active, `border-input-active`, and the token-change log. Read it before adding state styling to any component; none of it is repeated here. What follows is only what that doc doesn't cover:

- **`accent` has a split history.** Its purple was *wrongly* pulled into two component atoms (Checkbox, Input-field) from a Figma canvas artifact — the dashed stroke marking a selected component set — and removed there in #45, so it has **no consumer inside `components/`**. It also no longer has any `app/` consumer: `app/login/page.tsx:72`/`app/page.tsx:30` were the last two (the plain Phase-1 login UI), and #158's redesign rewrote both files without `accent`. `Architecture.md` §3.2 still lists it as a legitimate named semantic token (`#8A38F5`) — it is not deleted here, since retiring a token is an architecture-layer call, not a page-ticket's to make (`design/notes/LoginForm.md`'s "`accent` token — now fully orphaned" entry, `docs/HANDOFF.md`) — but it now has zero consumers anywhere in the repo, so there is nothing left to migrate before it can be retired.
- **Dark mode is still placeholder-only** (no Figma dark frames, no app-level `data-theme` switch yet) — open question, see `docs/open-questions.md#dark-mode-is-placeholder-only`.
- **`"use client"` precedent:** own state only when the behaviour is identical for every caller. `Dropdown` owns its open state; `Checkbox` stayed a Server Component and became interactive by switching its host to `<button role="checkbox">`. Leaf atoms stay presentational.
- **Ladle chrome theming still no-ops in `ladle:build`** (`appendToHead` emits an absolute `/@fs/` path) though it works in the dev server — relevant here because the visual-baseline job (#6) screenshots the built output, not the dev server. Status tracked in `docs/phase-log.md` (#49).
